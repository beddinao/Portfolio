2. FastAPI with SSL and API Key Validation

from fastapi import FastAPI, Header, HTTPException
import uvicorn
import os

app = FastAPI()

API_KEY = os.getenv("API_KEY", "default_key")

@app.get("/logs")
async def get_logs(authorization: str = Header(None)):
    if not authorization:
        raise HTTPException(status_code=401, detail="Missing Authorization header")
    
    if not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Invalid token format")
    
    token = authorization.replace("Bearer ", "")
    
    if token != API_KEY:
        raise HTTPException(status_code=403, detail="Invalid API key")
    
    return {"status": "success", "logs": ["Log entry 1", "Log entry 2"]}

if __name__ == "__main__":
    uvicorn.run(
        app,
        host="0.0.0.0",
        port=8443,
        ssl_keyfile="./certs/key.pem",
        ssl_certfile="./certs/cert.pem"
    )

Start Command:

python main.py

Test with curl:

curl -k -H "Authorization: Bearer default_key" https://localhost:8443/logs

6. Log Rotation and Last 50 Lines

I will use Python's approach to avoid blocking:

from collections import deque
import aiofiles

async def get_last_logs(file_path: str, lines: int = 50):
    try:
        async with aiofiles.open(file_path, 'r') as f:
            content = await f.read()
            all_lines = content.splitlines()
            return all_lines[-lines:] if len(all_lines) > lines else all_lines
    except FileNotFoundError:
        return []
    except Exception as e:
        return [f"Error reading logs: {str(e)}"]

Alternative with subprocess (faster for large files):

import subprocess

def get_logs_tail(file_path: str, lines: int = 50):
    try:
        result = subprocess.run(
            ['tail', f'-{lines}', file_path],
            capture_output=True,
            text=True,
            timeout=5
        )
        return result.stdout.splitlines()
    except:
        return []

7. API Key Handling Without localStorage

From my React experience in transcendence project:

import { useState } from 'react';

function App() {
  const [apiKey, setApiKey] = useState('');
  const [isAuthenticated, setIsAuthenticated] = useState(false);

  const handleApiKeySubmit = async (e) => {
    e.preventDefault();
    try {
      const response = await fetch(`${import.meta.env.VITE_API_URL}/status`, {
        headers: { 'Authorization': `Bearer ${apiKey}` }
      });
      if (response.ok) {
        setIsAuthenticated(true);
      }
    } catch (error) {
      alert('Invalid API key');
    }
  };

  const fetchLogs = async () => {
    const response = await fetch(`${import.meta.env.VITE_API_URL}/logs`, {
      headers: { 'Authorization': `Bearer ${apiKey}` }
    });
    const data = await response.json();
    console.log(data);
  };

  return (
    <div>
      {!isAuthenticated ? (
        <form onSubmit={handleApiKeySubmit}>
          <input
            type="password"
            value={apiKey}
            onChange={(e) => setApiKey(e.target.value)}
            placeholder="Enter API Key"
          />
          <button type="submit">Login</button>
        </form>
      ) : (
        <button onClick={fetchLogs}>Get Logs</button>
      )}
    </div>
  );
}

The API key stays in React state memory only. When user refreshes page, they need to enter it again. This is more secure than localStorage.

Reference: In transcendence project, we used React Context API for state management across components. Same principle applies here.

8. Two SSL Issues I Faced

Issue 1: NET::ERR_CERT_AUTHORITY_INVALID in Chrome

When I was working on my Inception project, Chrome blocked the self-signed certificate even after clicking "Proceed".

How I fixed it:

  • Installed mkcert tool: brew install mkcert (on Mac) or apt install mkcert (on Linux)
  • Ran mkcert -install to add local CA to system trust store
  • Generated certificates: mkcert localhost 127.0.0.1 ::1
  • Restarted browser
  • Now certificate is trusted automatically

Issue 2: Certificate paths not found in Docker container

In Inception project, my Nginx container couldn't find SSL certificates even though I mounted them.

How I fixed it:

  • Problem was relative vs absolute paths in docker-compose volumes
  • Changed from ./certs:/etc/nginx/ssl to absolute path
  • Made sure certificates were generated BEFORE building containers
  • Added this in Dockerfile to verify: RUN ls -la /etc/nginx/ssl/
  • Also changed permissions: chmod 644 cert.pem && chmod 600 key.pem
Reference: Both issues happened in my Inception project (github.com/beddinao/Inception) where I configured HTTPS for WordPress with Nginx.

10. Three Common Mistakes and How to Avoid Them

Mistake 1: Hardcoded API Keys and Ports

Problem: Putting API keys directly in code like const API_KEY = "abc123" or hardcoded ports like fetch('https://localhost:8443/api').

How I avoid it:

  • Always use .env files for sensitive data
  • Add .env to .gitignore immediately
  • Create .env.example file with placeholder values
  • Use environment variables: os.getenv("API_KEY") in Python, import.meta.env.VITE_API_KEY in React
  • Document required environment variables in README
Reference: In my transcendence project, we used .env for database credentials and API keys.

Mistake 2: CORS Misconfiguration

Problem: Forgetting to add CORS headers, or using allow_origins=["*"] which causes issues with credentials, or not handling preflight OPTIONS requests.

How I avoid it:

  • Set specific origins: allow_origins=["http://localhost:9240"]
  • Enable credentials if using cookies/auth: allow_credentials=True
  • List exact methods and headers needed
  • Test with browser DevTools Network tab to see CORS errors
  • Test from different browsers (Chrome, Firefox, Safari)
Reference: In transcendence project, we had CORS issues between React and Django that took time to debug.

Mistake 3: Wrong Certificate Paths in Docker

Problem: Docker container can't find certificate files because of incorrect volume mounting or wrong paths inside container.

How I avoid it:

  • Always use absolute paths in docker-compose volumes or paths relative to docker-compose.yml location
  • Verify files exist BEFORE building container: ls -la certs/
  • Add RUN ls -la /app/certs in Dockerfile to verify during build
  • Use docker exec -it container_name ls /app/certs to check inside running container
  • Set correct permissions: certificates should be readable (644), private keys should be secure (600)
  • Test locally first before Dockerizing
Reference: I faced this exact issue in Inception project with Nginx SSL certificates. Fixed by checking paths carefully and using docker exec to debug.
